How to use this handbook
This document consolidates every finding the team has recorded on connector tasks into one place: the shared findings document, the project documentation set, the client audit of 28 connector tasks, and the engineering discoveries made while building and hardening the tasks in this workspace.
It is written for someone who has just been handed their first connector task, and it is in three sections. Section 1 tells you which of the two task families you are holding. Section 2 is what a connector task is made of and what has to be true before you can run one. Section 3 is the work itself — how it goes, how long it takes, what goes wrong, and what the evidence has to show before it ships.
Reading order if you are short on time
* Part 4 — get the environment working. Nothing else matters until Docker, the platform flag, and Python 3.11 are right.
* Part 10 — the difficulty finding. This is the single highest-value section; it is the difference between a task that ships and one that comes back.
* Part 6 — the connector surface. The most frequent single defect across the audited batch.
* Part 19 — the checklist and the command sequence.
A note on sourcing
Where a number appears in this handbook it came from a measured run, a gate report, or the client audit — not from an estimate. Sections marked "Not in the current documentation" record findings made in this workspace that no existing doc covers; they are flagged so the guide owners can fold them in.


TIME EXPECTATION  Team members reported 2–3.5 hours to read the guidelines and understand the workflow, plus roughly 2.5 hours to get the environment working cleanly if nothing goes wrong. Budget a full day before you produce anything shippable.

Part 1 · Connector vs non-connector tasks
Two task families run through the same twelve stages, the same review record and the same acceptance bar — but they are packaged differently, configured differently, fail differently, and are audited against different pattern sets. Work out which one you are holding before you touch anything, because several of the differences are load-bearing and one of them is irreversible.

The connector healthcheck has a specific shape, and two of its fields are routinely set wrong:
[environment.healthcheck]
command = "curl -fsS --max-time 3 http://localhost:7000/health"
interval_sec = 15.0
timeout_sec = 120.0        # the ROUND-TRIP budget, not curl's --max-time
retries = 40
start_period_sec = 60.0    # boot grace; 120 for heavy startup
start_interval_sec = 15.0
* Bound the curl. Without --max-time 3, an unbounded curl hangs and every retry is consumed by one probe.
* Do not confuse the two timeouts. timeout_sec is the harness round-trip budget. Raising it is the fix for boot failures; never "fix" a healthcheck by editing the verifier timeout.

	1.6 What is identical across both families
Most of this handbook applies unchanged. Do not look for a connector-specific version of any of the following — there isn't one:
* The core quality invariant, and the Contract Gap / Coverage Gap split.
* The "four things" acceptance bar.
* The twelve stages, the cold read, and the forward and backward traceability passes.
* Write the prediction before hardening; re-run the oracle after every change.
* Oracle must score exactly 1.000. A partial oracle never justifies starting a battery.
* Exactly four battery attempts — never five, never "run five and pick four".
* The 14-row review.csv, both fold-ins, append-only notes, and the closing verdict line.
* Evidence discipline: a battery measures only the task as it existed when the battery ran.
* An infrastructure or verifier failure is ineligible evidence and gets replaced, never counted.

Part 2 · The connectors
A connector task is only as good as your understanding of the gym behind it. This part is what the connector layer actually is, how a request reaches it, how the two connectors in this workspace differ from each other, and how to probe a live gym before you design anything against it.
2.1 What a gym is
A "gym" is a service emulator: a FastAPI application backed by a per-tenant SQLite database, shipped inside the connectors-harness image. It exposes two quite different surfaces, and the distinction matters for everything else in this handbook:
* The MCP tool surface — typed tools (list_roles, search_channels, functions_deploy) that the agent is meant to use. This is the sanctioned interface.
* The control plane — /reset, /step, /state, and an /api/* family including sql-runner, download-db-file and delete-database. This is for the harness and the verifier, and the agent must never reach it.


Everything in Part 6 (closing the connector surface) exists because that second surface is reachable from inside the same container the agent runs in.
2.2 The fleet that ships in the image
The base image carries thirteen gyms and starts twelve supervisor programs — regardless of which single connector your task actually uses. This is measurable, not folklore:
$ docker run --rm --entrypoint /bin/sh <connectors-harness-image> -c \
    'ls /gyms; grep -c "^\[program:" /etc/supervisor/conf.d/supervisord.conf'
 
email_calendar   github      gws          linear     microsoft_365
microsoft_teams  notion      outlook      shopify    slack
snowflake        supabase    task-harness
12
WHY THIS MATTERS FOR YOUR TIMEOUTS  Your task uses one connector; the container boots all of them. That is why readiness takes 31–41 seconds on an emulated host, why the template's 40-attempt probe is too tight, and why memory pressure at container start is the single most common cause of a trial dying before it begins.
	2.3 The request path
Three parties reach the gym, by three different routes and with three different credentials. Knowing which is which is what lets you tell a security boundary from a bug.


Party
	Route
	Credential
	What it may reach
	The agent
	http://localhost:7000/mcp/<gym>
	None — the proxy is open on the MCP path
	Only the MCP tool surface. /mcp and /health are the sole client-public paths.
	The proxy
	Direct to the gym on its own port (e.g. 8025)

The gym decides what is privileged. These are the paths its gateway treats as control-plane, verbatim from the image:
_PRIVILEGED_PATHS = frozenset({
    "/reset", "/step", "/state",
    "/sql-runner",       "/api/sql-runner",
    "/download-db-file", "/api/download-db-file",

Note where /reset and /state actually live: they are served by the OpenEnv wrapper (custom_http_server.py), not by the gym's /api router. That distinction is what makes one gym's client-mode behaviour survivable and another's fatal — see 2.5.

	2.5 The two connectors in this workspace, and how differently they behave
Both tasks are connector tasks on the same harness. Almost nothing else about their connector layer is the same.




	Snowflake gym (port 8025)
	Supabase gym (port 8027)
	Shape
	SQL-backed. A tenant SQLite database with a real relational corpus.
	CLI-emulation. Roughly 126 emulated CLI commands rather than a queryable schema.
	Tool call convention
	EVERY tool wraps its arguments in an "input" object: {"input": {...}}. Calling any of them with {} returns "input: field required".
	Conventional argument objects.
	The escape hatch
	execute_sql_readonly runs arbitrary read-only SQL against the tenant database — including sqlite_master and WITH RECURSIVE. Any single figure is computable in one call.
	No general SQL tool. Source must be downloaded and read.
	State grading
	/state accepts verify_queries, so SQL-based database_state checks work.
	/state does NOT accept arbitrary queries — it returns a fixed shape. SQL-based database_state is unusable; grade the proxy-captured tool trace instead.
	Client mode
	FATAL if enabled. main.py drops the whole /api database router at import time.
	Harmless. Only the docs URLs are gated; the routers stay registered.
	

The client-mode difference is worth seeing in source, because it is the single most confusing behaviour in the stack:
# /gyms/snowflake/app/main.py
app.include_router(core_router)
if not client_mode_enabled():
    app.include_router(database_router)     # <-- never registered under client mode
 
# /gyms/supabase/app/main.py  -- no such conditional; routers always registered
openapi_url = None if client_mode_enabled() else "/openapi.json"
A SUBSTRATE PROPERTY IS DISCLOSED, NOT WORKED AROUND  Snowflake's general SQL tool means a solver that already knows what to compute gets any figure in one call. The accepted task did not try to close that — it recorded it as a property of the gym and moved the difficulty into DECIDING what to count. Where you cannot remove a shortcut, design so the shortcut does not help.
	2.6 Probe the live gym before you design anything
This is the standing discipline in this workspace, and it is what produced every connector finding in this handbook. Four checks, in order, against the running gym — never against a database file on disk.


#
	Check
	What it settles
	1
	DATABASE — does the tenant database exist, and where?
	For a SQL-seeded gym the tenant db only exists after POST /reset. Read it from /gyms/<gym>/mcp_databases/<dbid>.db, never from a stray file elsewhere in the image.
	2
	ROWS — how many rows in each table that matters?
	Gives you the corpus size you will design against, and the numbers your gold must reproduce.
	3
	THROUGH A TOOL — can the agent actually reach it?
	Prove it by a live tools/call, never by SQL against the file. A fact the agent cannot reach is not a fact your task can grade.
	4
	DOES ONE CALL RETURN EVERYTHING?
	The design question. If one call answers the task, you have no task yet — you have a lookup.
	

A worked probe, from a booted container:
# 1. seed the tenant, as the proxy does
CAP=$(cat /run/harbor/proxy/connector-control-capability)
curl -s -X POST -H "x-connector-internal-capability: $CAP" \
     -H 'Content-Type: application/json' -d '{}' \
     http://127.0.0.1:8025/reset
 
# 2. count what is actually there
ls /gyms/snowflake/mcp_databases/
sqlite3 /gyms/snowflake/mcp_databases/<dbid>.db \
  "SELECT name, (SELECT COUNT(*) FROM sqlite_master) FROM sqlite_master LIMIT 5;"
 
# 3. reach the same fact THROUGH the sanctioned tool surface
curl -s http://127.0.0.1:7000/mcp/snowflake-gym -X POST \
  -H 'Content-Type: application/json' \
  -d '{"method":"tools/call","params":{"name":"snowflake__list_roles",
       "arguments":{"input":{}}}}'

2.7 Connector-level defects you inherit
These are properties of the connector layer, not of your task — but they ship inside your package, so they are yours to detect and disclose.


Defect
	How it presents
	What to do
	Silent corpus loss
	A tool returns an incomplete list with no truncation marker and no continuation token. In one audited task the connector returned 22 items where the oracle enumerated 35 — and the 13 dropped rows included two the verifier expected.
	Run the golden's query path THROUGH the MCP tool and confirm the agent-reachable corpus equals the oracle corpus. Do this before designing, and again before shipping.
	Broken advertised tools
	The proxy /step call returns HTTP 200 while the agent sees an opaque "Tool call failed" with no diagnosable message.
	Exercise every tool the instruction references. A tool named in your prompt that returns nothing is a Contract Gap.
	Admin endpoints reachable
	The gym's /api/schema, /api/sql-runner or raw .db readable by the agent user.
	Probe as the agent user, not as root. Close them, or grade the trajectory so the bypass earns nothing.
	Ports open to anything
	With client mode off and no GYM_API_KEYS set, the gym ports are open to any local caller.
	If your proxy design requires client mode off, it must mint an API key so the agent still gets 401. The two designs are in Part 6.3.

Part 3 · What a good task looks like
3.1 The core quality invariant
One sentence governs everything else:
THE INVARIANT  The set of submissions the verifier rewards must equal the set a competent agent could produce from agent-visible information alone.
	

Every defect you will ever find is a violation of that invariant in one of two directions:


Direction
	What it means
	Typical shape
	Contract Gap
	The verifier rewards LESS than a competent agent could produce — correct, valid solutions fail.
	Hidden requirements, brittle regex, over-strict schemas, an undisclosed workflow rule
	Coverage Gap
	The verifier rewards MORE than intended — wrong or trivial solutions pass.
	Weak anti-hacking proof, unchecked edge cases, a backend bypass that skips the workflow
	

3.2 The acceptance bar — the "four things"
A task is accepted when all four hold at once. Every section of this handbook maps back to one of them.
* It grades cleanly — the checks measure concrete state, deterministically, and a correct solution passes.
* A model can solve it — at least one non-oracle run reaches full reward.
* Most attempts do not — at most 2 of 4 GLM-5.2 attempts strictly pass.
* Nothing is unfair — every graded requirement traces to a sentence the agent can read.


The three golden task principles
* Difficulty from work, never ambiguity. Every fork a reasonable engineer could take is pinned in instruction.md or promoted to its own graded question. Do not make a task hard by withholding requirements; make the work substantial.
* Deterministic and semantic grading. Grade identity, state and structure — database rows, API responses, configuration status — not vocabulary, whitespace or arbitrary prose.
* Strict packaging and provenance. Declared dataset provenance, and all 12 packaging gates green with no blocking findings.

4.2 Apple Silicon and the amd64-only image
The connectors-harness base image is published for linux/amd64 only. On an arm64 Mac every build and run goes through emulation.
export DOCKER_DEFAULT_PLATFORM=linux/amd64
 
# a pull without it fails with:
#   no matching manifest for linux/arm64/v8 in the manifest list entries
docker pull --platform linux/amd64 <image>@sha256:<digest>
* Cost of emulation: an oracle run goes from roughly 8 seconds native to 45–70 seconds emulated. Image builds take about 10 minutes.
4.3 Python 3.11 — not the system python
The pipeline needs Python ≥ 3.10, and its TOML reader uses 3.11's tomllib. The default python3 on macOS is 3.9.6 and fails the doctor's can_gate check with the misleading message "the bundle is incomplete".
# always use the explicit interpreter
/opt/homebrew/bin/python3.11 pipeline/run.py --doctor
 
# expected: every row "ok", including
#   Python >= 3.10 ... 3.11.11
#   TOML reader  ... tomllib
#   docker CLI   ... digest pinning available
4.4 The Dockerfile pre-bake — the OOM fix
Harbor's opencode install step runs nvm install 22 followed by npm i -g opencode-ai@latest at container start. Pre-baking the identical sequence at build time — where memory is unconstrained — makes the runtime step a fast no-op, because nvm reports "already installed" and npm's up-to-date check skips the download.
RUN apt-get update && apt-get install -y --no-install-recommends \
        curl bash coreutils nodejs npm ca-certificates && \
    rm -rf /var/lib/apt/lists/* && \
    su - rlgymagent -c 'set -euo pipefail; \

Part 6 · The connector surface
This is the single most frequent defect family in the audited batch: 13 of 28 tasks failed Layer 5 reward hacking, and 12 of those failed on one exact mechanism.
6.1 The three doors
Every connector task has three ways an agent can reach the graded data without using the sanctioned MCP tools. Close all three. Closing two is the same as closing none.


Door
	What it is
	How to probe it
	The state route
	The proxy's raw passthrough — GET /raw/{gym}/state?verify_queries=<arbitrary SQL>
	curl it from a bash shell inside the sandbox as the agent user
	The step route
	POST /raw/{gym}/step — drives the gym directly, skipping MCP
	Same: curl it as the agent user
	Files on disk
	The gym's SQLite database, /opt/proxy/server.py, seed SQL, anything world-readable
	ls and cat as the agent user; this is the door that makes the other two irrelevant
	

6.2 P-C1 — the unauthenticated raw-SQL proxy bypass
The harbor-mcp-proxy image exposes an unauthenticated raw passthrough on the same localhost:7000 the agent already reaches for MCP, and in some gyms the gym itself on port 8020 or a /api/sql-runner on 8014. An agent with a bash tool runs one SQL SELECT and derives every graded value, bypassing the entire sanctioned workflow. Because the verifier inspects only the final deliverable, the bypass yields full reward.


The pre-ship adversarial test — run this before you ship, from inside the sandbox:
# if either returns a row, the task is broken and does not ship
curl 'http://localhost:7000/raw/<gym>/state?verify_queries=SELECT 1'
curl 'http://localhost:8020/state?verify_queries=SELECT 1'
 
# also check what the agent user can read on disk
docker exec -u rlgymagent <container> sh -c 'ls -l /opt/proxy /gyms 2>&1'


What you can do about it as a task author
* Grade the trajectory, not only the deliverable. Add a tool_execution check that the sanctioned MCP tools were actually called. If reward depends only on final values, a backend-bypass rollout scores full reward.
* Verify the gate at runtime, not by reading the Dockerfile. A route you believe is closed is not evidence; a curl that returns 404 is.
* A latent route is a finding on its own. A run that happened not to take the shortcut does not prove the task is safe.


THIS IS A HARNESS DEFECT YOU INHERIT  The raw passthrough ships in the proxy image every connector author uses, so this is not your bug — but it is in your package, and therefore yours to close. The highest-leverage harness fix (authenticating the /raw/ passthrough) would close roughly 13 connector tasks at once.
	6.3 Gym-specific behaviour — not in the current documentation
This section records findings made in this workspace that no existing document covers. They matter because they look like drift between tasks and are actually two coherent designs that must not be mixed.
Two proxy designs, and how each authenticates to the gym

	Design B — API key
	Proxy variant
	The larger template proxy (~2051 lines)

Client mode is gym-specific
The gym decides whether client mode removes its control plane, and different gyms decide differently. The Snowflake gym drops its entire database router at import time when client mode is on:
# /gyms/snowflake/app/main.py
app.include_router(core_router)
if not client_mode_enabled():
    app.include_router(database_router)     # <- dropped entirely
 
# /gyms/snowflake/app/gateway.py
def client_mode_enabled() -> bool:
    explicit = (os.environ.get("GYM_CLIENT_MODE") or "").strip().lower() in {
        "1", "true", "yes", "on"}
    return explicit or bool(
        os.environ.get("HARBOR_CONNECTOR_CONTROL_CAPABILITY", "").strip())
* The condition is OR. Removing GYM_CLIENT_MODE is not enough on its own — a non-empty capability in the gym's environment also turns client mode on. Both halves are required.
* The Supabase gym does not do this. It gates only its docs URLs on client mode; its routers stay registered. The identical entrypoint configuration is therefore harmless on Supabase and consequential on Snowflake.
* The router that gets dropped serves /api/reset-database, /api/database-state, /api/sql-runner, /api/download-db-file, /api/delete-database — the whole state surface.


How to verify the boundary is actually correct, on a running container — this is the test that settles it either way:

docker exec -u rlgymagent <ctr> sh -c \
  'curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8025/state'
 
# as the proxy, with the capability: must be 200
docker exec <ctr> sh -c 'CAP=$(cat /run/harbor/proxy/connector-control-capability); \
  curl -s -o /dev/null -w "%{http_code}\n" \
  -H "x-connector-internal-capability: $CAP" http://127.0.0.1:8025/state'

Part 7 · The review record (review.csv)
Every task needs a review.csv at its root before shipping. This is a hard requirement, not an optional step.
7.1 Structure
* Location: tasks/<task-name>/review.csv, at the task root, included in the packaged zip at <task-name>/review.csv.
* Columns — exactly five: review_check, status, review_notes, change_made, what_to_record.
* Rows — exactly 14, byte-exact names. Never decorate a row name; the portal parser counts a decorated name as an extra row.
* Status values: PASS, FIXED_AND_VERIFIED, or N/A. N/A is legitimate only on Layer 4 · Connectors, MCPs, and CLIs for a non-connector task.
* change_made is BLANK on every PASS row. Truly empty — not "No change required". Writing anything there on a PASS row triggers a QC failure ("review.csv worksheet integrity"). Only FIXED_AND_VERIFIED rows carry content in that column; on an N/A row "No change required" is acceptable.
* Cross-trial · Calibration must END with an explicit verdict: Verdict: approve. / Verdict: change. / Verdict: block. — followed by the caveat a reviewer should weigh. A missing verdict line fails the calibration row.
* Check counts in the notes must match the shipped verifier. If the notes say "24 of 24" and the manifest has 34 checks, QC flags that the review's claims do not match the bundle. Re-derive every count after adding or removing a check.

7.2 review_notes is a history, not a final-state summary
When a row is revised across iterations, keep the original failure note and append the new state and evidence. Overwriting the original removes the only record that the first problem was real and was fixed — a reviewer then cannot tell whether it ever existed.
* No original failure may be overwritten or removed.
* Record the exact change made in every iteration.
* "Looks good", "fixed" and "reran" are not sufficient. Cite the specific trials, logs, files, artifacts or evaluation outputs inspected.


NEVER WRITE FIXED_AND_VERIFIED SPECULATIVELY  A failure closes only after the check that exposed it has been repeated and the post-fix evidence confirms the result. "I made the change" is not "verified".
	7.3 The contradiction to avoid
The status column and the notes must agree. A real example from this workspace: a task's review.csv marked Layer 2 Difficulty, Solvability and Stability all PASS, while the review_notes on those same rows read:
"ZERO reward files recorded under evaluations/difficulty (the directory
 is absent) - 0 of 4 ... 0/4 currently fails Layer 2 Difficulty"
 
"a true >=3 vendor-stability repeat is NOT yet recorded - an honest
 gap, disclosed"
The prose was honest; the status column was not consistent with it. The task's own Harbor Check verdict in the same folder recorded 16 Layer-2 failures. If QC reads review.csv against the shipped check verdict, that mismatch is itself a finding — on top of the underlying gap.
IF YOU HAVE AN OPEN GAP, SAY SO IN THE STATUS  There is no status value meaning "open gap", which is what tempts authors into writing PASS. Disclose it plainly in the notes AND do not claim PASS — an honest disclosed gap is recoverable; a contradicted PASS reads as a false claim.

Part 8 · Playbook — the two tasks worked end to end
This is the method applied end to end, followed by the two real tasks in this workspace worked issue by issue. Both started in exactly the same place — solved by the model in every scored run — and took different routes out. One route worked first time; the other spent a full cycle on a false negative. Read both.
8.1 Worked example A — the edge-function task
A Supabase Edge Function JWT audit. Go through every project in one workspace org, find every deployed Edge Function with JWT verification disabled, fix the genuine violations by redeploying with JWT on, leave the compliant ones alone. Deliverables: /workspace/metrics.json and /workspace/report.json.
Eight issues stood between this task and acceptance. They are worth reading in order, because six of the eight are consequences of the first.


A1 — The discriminator was a mechanical threshold, and stayed 4/4
* What it was. The rule was "only functions with version 2 or higher while keeping JWT disabled are violations" — disclosed and fair, but a one-step lookup. The model reads "version >= 2" and applies it directly.
* Evidence. Four difficulty runs, pre-hardening and hardened-v1, all scored reward 1.0 against this discriminator. Full disclosure did not move it.
* What was done. Reworked so the rule required interpretation, not lookup: "a function deployed for the first time is still in development — the developer may have intentionally left JWT off." The model must connect "first deploy" to the version field and derive the threshold itself.
* Two further nuances the seeded data already supported: public integration endpoints (health/signing, carrying an import map) and development-project prototypes (no import map) are exempt.
* Result. Genuine violations dropped from 11 to 3 — ids 46, 86 and 88: verify_jwt=false, redeployed, not a public endpoint, not a dev-project prototype.


A2 — The answer was migrated to the assertions but not to the prose
When the answer moved 11 → 3, the manifest's expected arrays were updated but the prose around them was not. The package asserted 3 and read 9.

THE ASSERTION FAILS LOUDLY; THE PROSE FAILS SILENTLY  A stale expected array breaks the oracle immediately. A stale why_justification breaks nothing and ships. A reviewer reads the prose.
	

A3 — task.toml grader metadata was still at v1
* GOLD listed violation_function_ids as 11 ids. Rewritten to 3 violations / 43 compliant, with the violation detail restated as 3 violations plus 8 compliant-despite-verify_jwt=false, each carrying its exemption reason.
* HOPS said "+ 11 deploy / 31 real tool calls". Rewritten to "+ 3 deploy / 23 tool calls" and "ONLY THE 3 REAL VIOLATIONS", with the 8-exempt note.
* DECOYS said "(11 ids)". Rewritten to "(3 ids)" with new lures: 11 = ignore all exemptions; 9 = apply only first-deploy; 43 functions_reviewed = slug-keying collapse.
* HIDDEN RULES actively called a now-compliant function "a real violation" — id 102 qz-sign. Reframed as "a public signing endpoint so compliant by policy, NOT a violation".


A4 — Two unpinned forks in the instruction
* Fork one. Two exemptions — public endpoint and development project — could both match one function, and the prompt did not say which governs. A model applying the dev-project rule to a public endpoint over-remediates and lands differently from the oracle.
* The pin. "Where a function's name and purpose mark it as a public integration endpoint, that classification takes precedence over the development-project rule, regardless of which project it lives in."
* Fork two. The violation_function_ids field definition literally said "every function that had JWT verification disabled" — contradicting the exemptions stated above it.
* The reconciliation. "every function you determined to be a genuine violation under the rules above — not the functions the rules above classify as compliant despite having JWT verification disabled."


A5 — The mirror was internally contradictory and would have broken the image
The mirror held gym_step_state expected_rows for ids 90, 94, 100 and 103 at remediated versions (6, 6, 5, 3) while the assertions already classified those functions as compliant and untouched. A correct v2 agent would have failed gym_step_state in the baked image.
Re-running the sync script from the corrected root brought those four ids to 5, 5, 4 and 2 — untouched seed state — and the mirror then diffed clean against root for instruction, task.toml and manifest.


A6 — Packaging gate findings
* G02 found the GLM gateway IP in eval files; G03 found authoring-machine paths in 9 eval files.
* Both auto-remediate — the gateway IP is rewritten to a TEST-NET-3 address, the paths to a generic user path. Gate-after showed 0 blocking, 1 package clean.
* The recurring part: this comes back every time evals are regenerated, because fresh eval files carry fresh machine paths. Always re-run the gate after an eval refresh.


A7 — The evidence was stale and had to be re-earned
Every evaluation on disk predated the v2 instruction edit: the runs timestamped 03:15, the instruction was edited at 10:52. The 4/4 and the 1.0 oracle were both measuring the old, easier task.
The re-earn order, and why it is that order:
* Re-run the oracle first against the v2 verifier — 3/3 violation, 43/43 compliant, 3 deploys, gym_step_state rows matching the corrected versions. If the oracle fails, that is a verifier defect, not a golden defect: fix the check and re-run.
* Then the 4-run battery, with the predictor written first: 11 = ignore all exemptions, 9 = apply only the first-deploy exemption, 3 = correct. If the battery does not produce 11 and 9 as the two predictable wrong answers, the discriminator is still a mechanical threshold in disguise.
* Then one solvability run from a non-oracle model — a full-reward run proves a model can do it, not merely that the check can grade the gold.


A8 — The review record was stale
The 14-row record still quoted 11 violations, 35 compliant, 11 deploys, "11/11 checks". Every count was stale. The instruction was to append, not overwrite: keep the original failure notes so a reviewer can see the first problem was real and was fixed, then add the v2 state and the new evidence on top — and re-zip from the sanitized tree, because zipping from raw source regresses the path and README gates.
8.2 Worked example B — the access-review task
A Snowflake least-privilege access review. The role roster reports direct grants, but Snowflake roles inherit up the hierarchy, and one grant is written ALL IN SCHEMA rather than against a table. Five figures follow from those two facts, plus a write-back that revokes the READONLY role's writes. Deliverable: /workspace/access_review.json. This task cleared the QC gate and finalisation.


B1 — It started 4/4 too
Same starting point as Task A: the delivery gate flagged it as solved in every scored run.


B2 — The prediction was written before the change
Prediction: band drops 4/4 -> 1-2/4, because a list must be exactly
right - missing, extra, or wrong-order all fail.
 
Result: matched.
Writing the prediction first is what lets you tell a working lever from a lucky one. The initial battery landed 3/4 before hardening; the hardened battery matched the prediction.


B3 — The lever was precision, applied honestly
Four of five deliverable fields changed from counts (10, 5, 6, 13) to sorted lists of names — the ten account names, five role names, six role names, thirteen table names. The fifth stayed a count because no name list existed in gold.
* Chained — you must enumerate correctly to produce the list at all.
* Sharp — a wrong list is a specific wrong answer, not a near miss.
* Provable — the oracle checks exact list equality.
* Honest — an auditor genuinely wants names. It raises required precision without adding ambiguity or removing information.


B4 — The oracle was re-verified after the change
Changing the deliverable shape from counts to lists could have broken grading, and there is no partial credit on the oracle gate. Re-running it returned reward 1.0 across 10/10 checks.


B5 — The exemption-precedence fork, pinned in four words
"How many roles can write" could defensibly include TRANSFORMER, which owns the tables, or include OPERATE-on-a-task. Two plausible exemptions, both matching the same question.
* The pin: "can write" became "are granted write". One change excludes ownership (not a grant) and task control from the count.
* The reinforcement: the prompt contrasts "how many roles are granted write" against "how many accounts could write" in the same sentence, so the asymmetry is legible rather than hidden.


B6 — The decoy table got a proof harness
A decoy table is an assertion unless something re-derives gold and catches collisions. This task shipped a consistency/ folder:

	gold_sql.py
	Re-derives every gold figure from the seeded tenant database, and exits non-zero if any decoy value collides with a gold value.
	shortcut_audit.md
	Records the lazy paths actually run against the live gym, and what each one scored.

	An independent cold-read pass, with instruction_sha256 stamped so staleness is detectable.
	

SHIP THE HARNESS, NOT JUST THE TABLE  No existing guide names the consistency harness as a deliverable, and it is what makes a decoy table defensible. A decoy table without something that re-derives gold and fails on collision is an assertion, not evidence.

8.3 Two things that look like hardening and are not
* Adding rules or instructions. A rule clear enough to be fair is a rule the model turns into a few lines of code — it reads it, copies it out, runs it. What you actually buy is boundary risk: runs failing on greater-than versus greater-or-equal, on which side of an as-of date a record falls, on a phrase that can be read two honest ways. That is vagueness dressed as difficulty, it points straight back at the sentence you added, and review will fail it.
* Adding data. Volume is not difficulty. A script crunches two hundred thousand rows as fast as two hundred.


THE TRAP DOES NOT TRANSFER  What is on offer depends completely on the task, and that is the point. The difficulty is a property of your data, not of your prose. A trap copied from someone else's task usually measures nothing on yours, because what made it work there was a property of their data.

8.5 The gotchas that cost batteries
The task is in band, but unfair
* Two honest methods give different answers. Fix the data so both agree, and keep values off thresholds rather than arguing about which side of one they fall.
* Every field the grade depends on must agree with itself across the whole input set — and you assert that AFTER the last edit, not before it.
* Dates break the story: a record after the as-of date, an override dated after the thing it overrides, an order column disagreeing with its timestamp. Assert all three every time.
* No two rules may apply to the same input at once, or a run can be right about one and still wrong about the grade.
* The last edit created a new ambiguity in a rule you did not touch. Re-check every rule after the final edit, including the ones you believe you left alone.
* The test is the trajectory, not the score. A run that reasons correctly and then writes "the spec would need to say" is telling you the task is unfair, whatever it scored.


The artifacts describe different tasks
* Prompt, solution, tests, manifest and environment drift on filenames, paths, columns or counts. Reconcile them on purpose, not by trusting a green oracle. Confirm the solution follows the required method, not just the reward.
* The reference answer's own write-up is graded by nothing, so nothing catches it repeating the mistake the task is built around. Read it against the standard line by line and recompute every figure it states from the inputs.


The measurement is wrong
* One battery is not a result. Report a rate only when every failure is traced to a named model error.
* Timeouts, empty runs, provider errors and memo-only failures are not kills. Triage every failed run to a step and a wrong value.
* Judge a failure by the delivered file, not by what the model said while working.
* Change one thing per version. Several edits at once make the result impossible to explain — and batch every content edit before you freeze, because each one voids the evidence before it.
* Pass rates multiply. A second trap on a working task often gives 0/4. Count traps that fire, not traps you planted.
* A four-trial sample carries about one trial of noise. One high battery beside two in-band ones is a sampling question, not a difficulty one — and it costs one more battery to answer.


Nothing moves
* After two builds with no change, stop turning the same dial. The tell is that every build so far moved the same thing.
* Volume is not a rung. More of the same pattern moves nothing.


WHEN THE LEVERS ARE GENUINELY SPENT  If remove-leakage, remove-recipe, add-a-real-second-deliverable, require-reconciliation and add-an-interpretive-discriminator have all been tried and the band is still 4/4, the task is not missing a discriminator — it is below the model population's capability floor. That needs a new data relation or a rework at the data level. Do not add a fourth independent rule; ten easy checks are still ten easy checks.
	8.6 Finalisation lessons from repairs
* Start from the exact version QC reviewed, not the newest working folder. Reproduce the reported example there and group findings that share a root cause before changing anything — this prevents several patches for what is really one problem.
* The instruction and supplied policy are the public contract. A verifier name, an internal comment or a golden phrase cannot impose a condition the participant was never told about. Either disclose the exact requirement or grade equivalent correct work fairly.
* Be strict only where the format is genuinely pinned. Filenames, schemas, codes and JSON keys can be exact when the instruction says so; memo wording and number presentation need room for natural alternatives.
* Read meaning, not keyword presence. Negation and contradiction checks must understand phrases such as "not reconciled" and "no longer current", and must stay within the correct record so one paragraph cannot accidentally pass or fail another.
* Give every verifier repair a positive and a negative regression. The exact valid phrase from QC should pass; a nearby version with the wrong meaning should fail. Cover ordinary layouts too — numbered lists, table rows, punctuation, line breaks.
* Each reward check measures the requirement in its own description. Two different checks should not both fail because one shared setup phrase broke, and a small memo issue should not carry the same loss as a missing core report.
* Keep golden files, grader code, hidden fixtures and answer keys outside the agent-readable workspace — and save complete run evidence: valid trajectory JSON, artifact manifests, detailed verifier output, rewards, and the model settings actually used. A good run is hard to defend when its saved record is broken.
* Do not change a sound task because QC returned INDETERMINATE or an obvious capture failure. Re-run first, then record a short evidence-based platform explanation if the same engine problem repeats. Task changes are for defects you can actually reproduce.

10.2 The honest levers
Hardening must add work, never remove information. The lever that worked on Task B is the textbook example.
The precision lever — Task B
Four of five deliverable fields changed from counts (10, 5, 6, 13) to sorted lists of names — the ten account names, the five role names, the six role names, the thirteen table names. The fifth stayed a count because no name list existed in gold.
* Chained — the model must enumerate correctly to produce the list at all.
* Sharp — a wrong list is a specific wrong answer, not a near miss.
* Provable — the oracle checks exact list equality.
* Honest — an auditor genuinely wants names, not just a count. It increases required precision without adding ambiguity or removing information.


Write the prediction before you change anything
This is what separates a working lever from a lucky one. Task B's prediction, written before the edit:

Result: matched.
Task A's equivalent prediction for its reworked discriminator was also written first, and doubles as a diagnostic:

 9 = apply only the first-deploy exemption
 3 = correct
 
If the battery does not produce 11 and 9 as the two predictable wrong
answers, the discriminator is not interpretive enough - it is still a
mechanical threshold in disguise.
10.3 Pin every fork — including exemption precedence
Where two exemption rules can both match one record, state which governs. This is a fork a reasonable reader could take two ways, and an unpinned fork is a Contract Gap.

STATE PRECEDENCE AS A PRINCIPLE, NOT A THRESHOLD  A precedence pin should read as a policy ("a public endpoint is a public endpoint wherever it lives"), not as a rule number. Then confirm the verifier's expected values actually reflect it.
	10.4 When nothing moves it — recognising a ceiling
Sometimes the interpretive levers have all been tried and the band is still 4/4. This is not a missing discriminator; it is a task below the model population's capability floor.
If you have tried removing leakage, removing the recipe, adding a real second deliverable, requiring reconciliation, and adding an interpretive discriminator, and it is still 4/4 — the task needs a new data relation (a second source to reconcile, a latent crux that fires on one row) or a rework at the data level.
DO NOT ADD A FOURTH INDEPENDENT RULE  Ten easy checks are still ten easy checks. Adding breadth to a task that is too shallow does not make it discriminating; it makes it longer.
	10.5 "Too easy" is usually a symptom
Before you tune difficulty, close the shortcut. Most audited connector tasks flagged as too easy were inflated by the proxy bypass described in Part 6 — the agent answers correctly without performing the workflow at all. Closing that bypass routinely moves a task from trivially solvable to genuinely discriminating with no content change whatsoever.
ORDER OF OPERATIONS  Close the bypass and fix the grading first. Re-measure. Only then decide whether the task is genuinely too easy. A task that is 4/4 because one SQL SELECT answers it is not easy — it is broken.

The documentation is strong on static defects and on attribution. These four findings are all migration-shaped, and they are the ones that most reliably send a hardened task back.

Part 12 · Verifier design and fairness
88% of tasks failed at the verifier coverage and fairness gate. More than 60% had verifier-only requirements; more than 50% had verifier false-negatives counted as model failures. This is where most of the remaining rejections live.
12.1 Traceability — the most common defect
Every graded requirement must trace to a sentence in instruction.md. The backward pass is the mechanical way to find violations: for every check in the manifest that is not on your list from the cold read, quote the sentence that creates the requirement — or delete the check.
This applies to workflow and trace-shape checks too, which is where connector tasks specifically fail:
* Every tool_execution check must trace to an instruction line.
* Every rubric "fail if fewer than N calls/reads" rule must trace to an instruction line.
* Every definitional count (do bots count as people? which field is the account identifier?) must be stated in the instruction — the verifier must not hard-code one side of an ambiguous definition.


Real examples of undisclosed workflow requirements


Task
	The hidden requirement
	Consequence
	outside-bookers-confirmed-group-session-audit
	A reward-bearing rubric graded a prescribed first full-window search_calendar call that instruction.md never states.
	Two evidenced runs with fully correct answers were penalised.
	tracker-signoff-holdback-reconcile
	A check awarded 5% of reward for a bare ">=10 accepted tool calls" floor with an EMPTY expected_tools list, plus a rubric failing any trace with "fewer than seven tab reads".
	Penalised an equally correct whole-workbook grid read.
	ephyra-final-stretch-second-reviewer-coverage

12.2 Dead score buckets and vacuous checks
A manifest that declares weighted buckets (sql 0.3 / state 0.2 / rubric 0.5) while sql_verifiers is empty, the state axis is disabled with an empty expected_diff, and rubric.toml holds only a system preamble with zero items — is advertising coverage that does not exist. Worse when the README then describes that dead layer as active.
* Every weight bucket declared in the manifest must have a selector matching at least one check.
* A disabled bucket must be explicit, and the remainder reweighted.
* A tool_execution check with an empty expected_tools verifies nothing — name the required tools or delete the check.
12.3 Duplicate checks and scoring disproportionality
Two failure shapes, both caught by one test.
* Duplicates: byte-identical specs (answers_json_exists and answers_json_parses) double-counting the same fact.
* Implied checks carrying independent weight: answers_json_wellformed is logically implied by each of the four value checks, yet carried 20% of reward.


THE TEST  If a wrong answer to the central question the task exists to answer still scores most of the marks, the verifier does not measure the task. In one audited task the headline question was worth the same 0.2 as a file-parses check, so a run that answered it wrongly still scored 0.8.
	12.4 The judge configured over an empty rubric
A judge is configured in task.toml and is a hard precondition of the scoring path, yet rubric.toml contains zero rubric items and every graded check is a deterministic file_check. When the API key is unset or the judge model is unreachable, the scoring function returns 0.0 BEFORE any file_check runs — converting a configuration failure into a scored zero on an all-deterministic task.
* If rubric.toml has zero rubric items, the judge must not gate the scoring path.
* Lint rule: zero rubric items means task.toml must not set a verifier judge.
* Judge infrastructure failures must be ineligible, never a 0.0 reward scalar. An infrastructure fault must never become a result attributed to the model.
12.5 Verifier categories — keep core, and look before you delete
Every verifier entry in the manifest carries a "category". The trainer workflow for mined Harbor tasks states the rule bluntly: keep "core", delete every "secondary" entry, and do it BEFORE the oracle run because it changes the grading. That rule is sound and all three tasks in this workspace already satisfy it — none of them ships a secondary verifier.
$ python3 -c "import json,collections; ..."   # count categories per manifest
 
read-only-in-name-only                {'core': 12}
the-edge-function-nobody-locked-down  {'core': 9, 'process': 2}
what-the-loads-quietly-lost           {'core': 10}
Note the third category. The trainer rule assumes every verifier is core or secondary, and a connector task can carry a "process" entry that the binary model does not describe. In the edge task those two are report_explains_the_jwt_policy (a file_check) and states_a_clear_conclusion (the task's only rubric_check).
DO NOT APPLY "DELETE EVERYTHING NOT CORE" MECHANICALLY  On that task it would remove the only judged item in the bundle and silently convert it to fully deterministic — which changes what the package measures, not just how many checks it has. Count the categories first, and treat anything that is neither core nor secondary as a decision, not a deletion.
	12.6 An ask may legitimately stay ungraded
The backward pass says every ask is either graded or deleted. There is a third state, and the accepted task uses it deliberately.
Task B's instruction says "State your conclusion in your reply." Nothing grades it. Its task.toml records that this is deliberate: adding a response_check "would put a judged verifier on a bundle that is otherwise 100% deterministic". The sentence exists for framing — it makes the task an access review rather than a scripted five-number exercise.
RECORD THE DECISION, DO NOT FORCE THE CHECK  An ask may legitimately stay ungraded when grading it would force a judge onto an otherwise-deterministic bundle. Following the backward pass literally would delete that sentence or add a check; the accepted task did neither, on purpose — and wrote down why.

13.2 Building the evaluations structure
Trials land in eval-jobs/. The package needs them reshaped into evaluations/. Sort oldest-first so r1..r4 are in run order.
TASK="tasks/<task-folder>"
BATT="eval-jobs/<job-name>"

for i in 0 1 2 3; do
  r=$((i+1)); SRC="${TRIALS[$i]}"; DST="$TASK/evaluations/difficulty/r$r"
  rm -rf "$DST"; mkdir -p "$DST/agent" "$DST/verifier"
  cp "$SRC/result.json"                    "$DST/result.json"
  cp "$SRC/config.json"                    "$DST/config.json"
  cp "$SRC/agent/trajectory.json"          "$DST/agent/trajectory.json"
  cp "$SRC/verifier/reward.json"           "$DST/verifier/reward.json"

  cp "$SRC/verifier/verifier_summary.json" "$DST/verifier/verifier_summary.json"
done
solvability/r1 takes any reward-1.0 trial from a non-oracle agent. stability/repeat-01..03 is a verifier REGRADE — the same frozen trajectory graded three times — not three fresh runs. 13.3 Reading the results without drawing the wrong conclusion
Three traps sit between a finished battery and a number you can report. Each of them turns a healthy task into a bad one on paper.


Trap
	What happens
	What to do instead
	verifier_summary.json repeats itself
	The file lists the same verifiers several times under different groupings. Grep for "passed" and pair it with a nearby "name" and you will attribute a failure to the wrong check — then "fix" a verifier that was never failing.
	Read whole entries, not adjacent lines. Parse the JSON and print each item with its own name, type and motivation together.
	A reward of 0.0 that was really a crash
	A trial that died still writes a reward, and 0.0 counts as a model failure unless you look.
	Before counting any zero, check for exception.txt and for a MISSING trajectory.json. Either one means the run is void evidence and must be replaced, never counted as difficulty.
	Concurrency starving the containers
	Each running container asks for about 4 GB. Over-subscribe and the machine swaps; a starved container looks exactly like a failed task.

13.4 When the golden trajectory is missing or wrong
A broken or absent golden trajectory does not have to block the battery. The order is flexible: fix the gold first, or run the battery and then promote a fully-correct run into it.
* Promote a reward-1.0 run. Take a model run that scored exactly 1.0 — or the best available — and make it the golden trajectory. This is the recommended way to get a clean gold when the original is broken.
* But the gate is unmoved. Before submission the task must have a golden trajectory AND the oracle must score exactly 1.000. Promoting a run does not excuse either.


A PARTIAL ORACLE IS NEVER A STARTING GUN  If the oracle is below 1.0, a verifier is rejecting the known-correct answer. That is a defect in the task, not in your setup, and not something a battery can tell you anything useful about. Fix the owner — gold, rubric, or an ungrounded check — and re-run before spending a single model trial.
	13.5 What makes evidence stale
* The write-up quoting results, a pass count, a fingerprint, check counts or call counts from a battery that later runs replaced.
* Repeats described with the wrong count and the wrong nature — "three fresh oracle repeats" where the folder holds five re-gradings of a model run.
* Evidence described as living somewhere it does not.
* A review record describing a different task entirely, or mixing up two batteries.


THE FIX IS MECHANICAL  Re-derive every number in your write-up from the evidence folder and the manifest before you finalise. None of these gaps needed judgement to find — they needed somebody to re-derive the number. And DELETE stale claims rather than updating them; a write-up asserting something the package contradicts is a finding on its own.
	

YOUR OWN PROSE IS GRADED  The reviewing agent reads every file in the tree. A comment explaining WHY a design is correct helps you. A comment explaining why a defect is tolerable gets quoted straight back at you. Never ship a to-do, a note asking somebody else to fix something, or a line conceding that a check is questionable. Keep repair notes outside the package.
	13.6 Attribution — whose fault was the run
Reading runs is where a task is saved or lost. The discipline is to label every failure by cause before drawing any conclusion about difficulty.


Observation
	Attribution
	The judge quotes words the model never wrote
	Grading defect — never a model failure
	The attempt aborted before the agent started; the only log is image-baked
	Infrastructure. The attempt is INELIGIBLE and must be replaced, never counted
	The deliverable was exactly right but one check pulled it below full reward

Part 15 · The QC review workflow
QC is run as a two-pass review with isolated context. The second pass is the point — it exists to catch anything hallucinated or overlooked in the first.
15.1 The common issues QC is looking for
* Task checksum mismatch
* Instruction-to-verifier mapping issues
* Verifier coverage and fairness (88% of tasks failed here)
* Verifier-only requirements (more than 60% of tasks)
* Verifier false-negatives counted as model failures (more than 50% of tasks)
* Unfair verifiers — verifying something not mentioned in the prompt, ambiguous requirements
* Oracle mode failure
* Not grounding verifier quality against the GLM runs
15.2 The strategy
* Separate the two kinds of correctness. Structural correctness of the task is a different question from model-failure correctness. Do not mix them.
* Get instruction-to-verifier mapping right BEFORE running GLM. Use both LLM review and manual reading. There is no point spending battery time on a task whose contract is wrong.
* Then run GLM, and read the trajectories. Trajectories are necessary for confirming verifier quality. Some defects are only visible there — for example, ambiguous data that is not in the prompt but comes from the connector's seed data.
* Review twice, with isolated context. A second pass in a fresh session is the key control.
* Ask follow-up questions. Interrogate whether a failure is genuine rather than accepting the first verdict.


15.3 The unified QC tool
A standalone reviewer ships alongside this work: one command checks a task against three gates — prompt and environment, verifier, run evidence — and returns an advisory Keep / Fixable / Reject with cited evidence. It never edits the task.
# free, makes no API call - start here
python3 unified_qc.py --input /path/to/<task-dir> --dry-run
 
# real review
python3 unified_qc.py --input /path/to/<task-dir> --output-dir ~/qc-out/<task>
 
# post-run QC: reviews your actual harbor runs
python3 unified_qc.py --input /path/to/<task-dir> \
  --trajectory <job-dir> --include-trajectories required
It reads the same variables as harbor run — OPENAI_API_KEY, OPENAI_BASE_URL, JUDGE_MODEL — so a sourced harbor env is enough. Outputs are results.json (full evidence and the ask-to-verifier coverage map), results.csv (one row per issue), and summary.md.
* It is advisory. A model assists the analysis; a human confirms the cited evidence before acting. Do not auto-act on the verdict.
* Check the trajectory actually matched. If you pass --trajectory, confirm context.trajectory.records is greater than zero in results.json before trusting the run gate. Zero means nothing matched and the gate proved nothing.
* A crashed run is flagged as infrastructure, not difficulty. Discard that reward and re-run. Never let a crash enter a pass rate as evidence the task is hard.
15.4 The review discipline that matters most
DO NOT TRUST README OR review.csv  Before reading README or review.csv as ground truth, do your own independent pass. Reproduce the behaviour yourself — run it, trace it, inspect the actual artifacts and logs — rather than accepting a stated verdict. Only after forming your own conclusion, cross-check against the documents. Treat any mismatch as a flag to call out explicitly, not something to silently resolve in favour of the existing doc.
	

Audit review.csv as its own artifact, separately from the task outcome: missing or duplicate rows, inconsistent gate labels, contradictory verdicts, malformed data, or rows unsupported by any evidence in the folder.


The mandatory model-failure sanity check
Regardless of what any skill's default checks cover, explicitly re-verify and give a Yes/No/Uncertain verdict with specific evidence (file path plus line or section) for each:


Check
	The question
	Reward hacking
	Did the task pass via a shortcut or exploit rather than genuine completion?
	Unfair verifier
	Did the verifier require something not implied by the spec, or penalise a legitimate approach?
	Non-model-caused failure
	Did it fail due to harness, environment, judge infra, a flaky verifier, an ambiguous spec, or a one-off bug — rather than a genuine model capability failure?
	

If uncertain, say so explicitly rather than guessing. "Uncertain — could not verify" is a valid and useful answer; a confident wrong verdict is not.

16.4 task.toml ordering — an upload trap
The upload validator requires schema_version as the FIRST line of task.toml. Without it the parser fails to find [task].name even though the TOML is syntactically valid — the validator is not using a standard TOML parser.
schema_version = "1.1"
 
[task]
name = "harbor/your-task-name"
description = "..."
keywords = ["harbor"]
 
# top-level keys like artifacts go AFTER [task]
artifacts = [
    { source = "/workspace/metrics.json" },
]
After fixing, mirror to environment/_app/task.toml via sync_app_mirror.sh and re-run --check-only to re-zip.
16.5 The MCP proxy bootstrap anchor
A package can be rejected at upload with: "environment/mcp/proxy/server.py could not be schema-repaired: no known bootstrap anchor" — even after passing every preceding gate. It mainly affects packages built from mined proxies rather than template-based ones.
The upload pipeline performs schema-repair on the proxy by locating a fixed text anchor inside bootstrap(). It searches for a specific 11-line block at exactly 12-space indentation.


EXACT TEXT MATCHING, NOT BEHAVIOURAL EQUIVALENCE  Restoring the same function calls with different indentation (16-space instead of 12-space) or reworded comments will still be rejected. Copy the block verbatim from an accepted package rather than reimplementing equivalent logic.
	

The required block, at exactly 12-space indentation:
            # Tool catalog assignment
            state["tools"] = tool_list
            logger.info(f"Registered {len(tool_list)} tools for {name}")
 
            # HARBOR-LOCAL: warn loudly when any tool carries a schema
            # that the model family is known to mishandle
            _warn_schema_issues(name, state["tools"], run_model)
 
            # Verify allowlist size
            if allowlist and len(state["tools"]) != len(allowlist):
                logger.warning(f"Tool count mismatch: expected {len(allowlist)}")
The one-line verification — it must return 1:
grep -c "HARBOR-LOCAL: warn loudly when any tool carries a schema" \
  environment/mcp/proxy/server.py


The coordinated changes required alongside it: add the helper functions (_is_fireworks_family, _warn_schema_issues, _schema_problem_keys_for_model); move the run_model assignment before the async server loop to prevent unbound-name errors; move tool-list processing outside the gym-only conditional so it executes at 12-space indentation; and place the catalog normalisation call just before STATE[name] = state.


A related trap: the converter matches server.py by full file hash
Task B hit upload rejection on server.py three times — a "# HARBOR-BOOTSTRAP" comment marker, then patching the reference — before finding the fix: ship the exact unmodified reference server.py and adapt the ENTRYPOINT around it. Do not modify the reference proxy to suit your task.

Part 17 · Docker and entrypoint engineering
NOT IN THE CURRENT DOCUMENTATION  This part records findings made while building and repairing the environments in this workspace. No existing document covers them. They are ordinary Dockerfile engineering, but each one produced a real, silent failure here.
	17.1 A semicolon-separated RUN swallows failures
Docker takes the exit status of the LAST command in a RUN. A block of commands joined by semicolons, with no set -e, reports success if the final command succeeds — no matter what failed in the middle.
$ sh -c 'false; true'; echo $?
0
In the task images this pattern covered the block that rewrites supervisord.conf — reassigning user=root to user=gym and relocating every log path. A failed sed there produces a green build with a broken supervisor configuration. The fix is one line plus an assertion:
RUN set -eu; \
    id rlgymagent >/dev/null 2>&1 || useradd --create-home ... ; \
    sed -i -e 's/^user=root$/user=gym/' ... \
        /etc/supervisor/conf.d/supervisord.conf; \
    grep -q '^user=gym$' /etc/supervisor/conf.d/supervisord.conf || \
        { echo "supervisord.conf was not rewritten" >&2; exit 1; }


KEEP pipefail WHERE THERE IS A PIPE  The Node pre-bake pipes curl into bash. Without set -o pipefail, a failed curl still succeeds because bash exits 0 on empty input. Use set -euo pipefail inside that su -c block specifically — set -eu alone is not enough there.
	17.2 Layer order decides your rebuild time
If the expensive Node/opencode layer sits AFTER the COPY of task files, then editing instruction.md or any test invalidates it and re-downloads nvm, Node and opencode on every single build. During a hardening cycle you edit those files constantly.
The ordering rule: everything that depends only on the base image goes first; task-file COPYs go last. Only the permissions step that genuinely depends on the copied files stays after them.


Order

	The rlgymagent user from step 1

	Base image only
	4

	Your task files

17.4 The readiness probe and how long boot actually takes
The entrypoint waits for the proxy before handing the container to the agent. The template allows 40 attempts, roughly 40 seconds. That is too tight on an emulated host, because supervisord starts the full 12-connector gym fleet regardless of which one the task uses.


Task
	Measured time to readiness
	Against a 40-attempt limit
	Snowflake task
	31 s
	Would have passed — with 9 s of margin
	Supabase task
	41 s
	Would have FAILED
	

Both measurements are from the same host on the same afternoon. Raising the budget to 150 attempts costs nothing when the proxy comes up quickly, and prevents a whole class of spurious "proxy did not become ready" aborts.


The readiness check should test both listeners where the proxy provides both:
while [ "${PROXY_ATTEMPT}" -lt 150 ]; do
    if [ -S "${TRUSTED_PROXY_SOCKET}" ] \
        && curl -fsS http://127.0.0.1:7000/health >/dev/null 2>&1; then
        PROXY_READY=1; break
    fi
    ...
CHECK WHICH PROXY YOU SHIP FIRST  The smaller template proxy creates no trusted socket. On that proxy the socket test never passes and the container hangs until the probe gives up. Its absence from that task's readiness check is correct, not an oversight. See Part 6.3.
	

REPEATED HEALTHCHECK FAILURES DURING BOOT ARE NORMAL  While the gyms come up you will see Healthcheck failed (rc=7, in_start_period=True) over and over. That is the probe doing its job — it retries up to 40 times. You only have a problem if "Healthcheck passed" never appears at all. If it never does, the usual cause is memory pressure rather than a broken image: lower the concurrency and retry before touching the Dockerfile.

Part 18 · Triage — when QC fails
18.1 The infrastructure-shaped failure
You will see failures of this shape:
Run failed: Harbor Check wrote no durable status:
  [job]: RUNNING · [job]: RUNNING · [job]: FAILED ·
  harbor-check: The Batch stage failed; exact original error evidence
  could not be verified for this invocation.
The standing guidance is that this is an infrastructure problem, not a task verdict — re-run QC, and if it fails the same way, flag it to the QC team. That guidance is right, and it is also incomplete: it describes the SYMPTOM, and a task can produce that symptom deterministically.


SEPARATE THE ABORT FROM THE VERDICT  A "no durable status" abort means the harness died before writing a result. That is different from a recorded Layer-2 failure. Re-running clears the first and never clears the second. Check whether your task ALSO has a standing verdict failure before concluding it was just infrastructure.
	

Task-side conditions that produce an abort with no status
* The agent install OOMs at container start (exit 137) because the image has no Node/opencode pre-bake. The job dies before any verdict exists.
* The readiness probe gives up before the proxy comes up, so the trial aborts in preparation, before agent setup.
* The healthcheck times out in the lifecycle (P-C2) — the only proxy log captured is the image-baked one, timestamped before the run.


All three are fixable in the package, and all three are covered in Part 4 and Part 17.
18.2 How to read a Harbor Check result
The check writes a per-subcheck verdict. Summarise it by layer before drawing any conclusion — the shape of the failure tells you what kind of problem you have.
/opt/homebrew/bin/python3.11 -c "
import json, collections
d = json.load(open('evaluations/harbor_check/check-result.json'))
by = collections.defaultdict(lambda: [0, 0])
for k, v in d.items():
    if not isinstance(v, dict): continue
    by[k.split('__')[0]][0 if v.get('outcome') == 'pass' else 1] += 1
for l, (p, f) in sorted(by.items()):
    print(f'{l:35s} pass={p:2d} fail={f:2d}')"


A real result, from a task whose evidence folder was emptied after an edit:
layer1_clarity_scope                pass= 5 fail= 0
layer1_package_consistency          pass= 8 fail= 0
layer1_realism_leakage              pass= 5 fail= 0
layer2_difficulty                   pass= 0 fail= 5
layer2_solvability                  pass= 0 fail= 5
layer2_stability                    pass= 0 fail= 6
layer5_llm_judge_design             pass= 7 fail= 0
layer5_reward_hacking_static        pass= 5 fail= 0
layer5_verifier_fairness_static     pass=13 fail= 0
43 pass, 16 fail, and every failure in Layer 2. That shape means the CONTENT is sound and the EVIDENCE is missing — the check's own words were "evaluations/ exists but is empty". No amount of re-running clears that; only running the battery does.


The triage question, in order
* Did the run produce a verdict at all? No verdict means an abort — check the environment first (Part 4, Part 17).
* If there is a verdict, which layers failed? Layer 2 only, with Layers 1 and 5 clean, means missing evidence rather than a broken task.
* Does the evidence exist on disk? Confirm evaluations/difficulty, solvability and stability are actually present and populated.
* Has a battery ever been run for THIS task? Check the job output directory. It is easy to assume a battery ran because a sibling task has one.
# which task does each recorded job belong to?
for d in eval-jobs/*/; do
  printf '%-28s ' "$(basename $d)"
  grep -rhoE 'harbor/[a-z-]+' "$d" 2>/dev/null | sort -u | tr '\n' ' '; echo
done

	Agent crashes with "text part chatcmpl-… not found"

	First run is very slow

Part 20 · What the guidance does not cover
Two things a reader needs to know before trusting the surrounding documentation: which governing files are missing here, and which behaviour no document describes. Both cost real time to rediscover.
20.1 Missing artifacts in this workspace
* REVIEW-STANDARD.md (the single authority for review.csv) and AUDIT-STANDARD.md (the five-layer audit framework and the shipping band) live at the OBI project root, alongside audit-framework.toml, which defines the 14 areas and their named subchecks. None of the three is present in this connector-tasks workspace, so anyone working only from here has no copy of the governing rules. Copy them in, or treat this handbook as the local stand-in and re-check it against them before relying on a band or a row definition.
20.2 Undocumented environment behaviour
* The two proxy designs and their incompatible entrypoint requirements (Part 6.3).
* Gym-specific client-mode behaviour — the Snowflake gym drops its database router, the Supabase gym does not (Part 6.3).
* Silent-failure Dockerfile semantics, layer ordering, and build-context pollution (Part 17).
* Measured readiness timings and why the template budget is too tight on an emulated host (Part 17.4).
